# AgentOps 多智能体项目编排

当用户给出一个最终目标，或要求继续、恢复、审查一个 AgentOps 项目时使用本 Skill。目标是把工作变成可追踪、可验证、可交付的项目，而不是只给建议。

## 固定角色

- `orchestrator`：主智能体，负责理解、决策、调度、Git、文档和最终交付。
- `market-manager`：市场、用户、竞品、替代方案和开源复用研究。
- `requirements-analyst`：范围、需求、用户故事和验收标准。
- `architect`：架构、接口、数据流、技术选型和 ADR。
- `coder`：独立分支或 worktree 中的最小实现和自测。
- `tester`：独立测试、边界、回归、安全和证据记录。

## 启动流程

1. 读取 `AGENTS.md` 和 `docs/agentops/` 下的项目文档。
2. 如果 `PROJECT.md` 仍是空模板，把用户目标转成项目合同；只在存在重大歧义时做一次集中确认。
3. 创建或更新 `TASKS.md` 任务图，写明依赖、负责人、允许修改路径和验收条件。
4. 按依赖依次调用市场、需求、架构、编码和测试智能体。派发前读取对应 `.codex/agents/*.toml` 的 `developer_instructions`，把角色指令、任务卡、允许修改路径和交接格式一起传入；不要只传角色名称。
5. 独立并行任务使用互不重叠的文件范围和 worktree；不要让多个编码智能体编辑同一文件。
6. 每次状态变化更新 `STATE.md`；重要技术选择写入 `DECISIONS.md`；验证结果写入 `EVIDENCE.md`。
7. 使用功能分支和 PR 管理改动，禁止直接修改或自动合并 `main`。
8. 主智能体检查证据、范围、文档一致性和未解决风险后，汇总最终交付给用户。

## 能力选择

优先使用 Codex 原生 Agents、Skills、worktree 和 review；然后使用已审核插件、MCP 和白名单开源项目；最后才编写最小实现。引入第三方能力前读取 `docs/agentops/OPEN_SOURCE.md`，记录来源、版本、许可证、用途和风险。

## 风险门控

删除数据、付费、发布、部署、权限变更、合并 `main`、引入未审核代码和重大需求歧义都必须请求人工确认。不要为了让流程继续而绕过风险门控。

## 恢复与交付

用户要求继续时，从 `STATE.md` 的“下一步”和 `TASKS.md` 的未完成任务恢复，不重复询问已经记录并确认的信息。

最终交付必须包含：交付物位置、使用或运行方法、测试证据、已知限制、Git/PR 状态、未完成事项和后续建议。没有证据的内容不得写成已完成。
